# 知澜 v0.2 安全可用性升级设计

> 日期：2026-08-23  
> 状态：已批准实施（项目负责人已授权自主完成设计、开发、验证与 GitHub 推送）  
> 目标：把当前安全垂直切片升级为可日常试用、可持续演进且不会误称为生产完成的 v0.2。

## 1. 背景与决策

当前仓库已经具备安全入库、租户/所有者两级可见性、关键词证据检索、引用约束回答、飞书事件接入和会议提醒。基线的 51 个测试、类型检查和构建均通过，模块边界也足以继续演进。因此本轮不重写项目。

审计同时复现了三个阻断问题：幂等映射可导致同租户跨用户读取 owner-only 资产；最短四字符密码会被“末四位预览”完整持久化；标题、来源元数据和提醒标题可绕过正文脱敏。产品 API 还直接信任调用方提交的租户/用户请求头，不能暴露到生产网络。搜索只扫描最近 500 项，旧资产永久不可检索。

本轮采用“安全可用的模块化单体”方案：先建立可验证的安全不变量，再在同一架构内补齐数据库检索、分页与生命周期、认证、飞书交互和交付工程。暂不直接引入 PostgreSQL、消息集群、向量数据库或桌面壳；这些能力需要真实部署条件和产品反馈，盲目加入只会增加运维面。SQLite 明确限定为单实例试点存储。

## 2. 成功标准与范围

本轮完成后必须满足：

1. 相同租户的不同用户无法通过幂等键、资产 ID、列表或搜索读取 owner-only 内容。
2. 普通持久层、API 响应、日志和 LLM 证据中不保留识别到的秘密字符；标题和来源元数据遵守同一规则。
3. production 模式禁止信任身份请求头，必须验证有期限的 HMAC Bearer Token；development/test 保留显式开发模式。
4. 资产超过 500 条后仍可检索；资产列表支持稳定分页和筛选。
5. API 客户端错误返回正确状态码和统一错误结构，并带 request ID。
6. 会议时间按显式时区严格解析，非法日期和过去时间不会被静默归一化为有效提醒。
7. 飞书用户可使用帮助、搜索和问答指令；所有回答继续遵守权限与引用降级规则。
8. clean clone 可通过一条验证命令完成类型检查、测试、构建及关键安全回归；GitHub CI 自动执行同一质量门。

本轮不宣称完成飞书 OAuth、源文档 ACL 同步、多副本部署、向量检索、云文档增量同步、Web/桌面 UI 或完整审计平台。README 和健康接口必须如实标注这些边界。

## 3. 架构与组件

### 3.1 安全规范化边界

所有原始输入先进入字段级安全规范化器，再允许派生标题、提醒、索引或模型证据。正文和标题使用相同的秘密检测；持久化遮罩只保留秘密类型，不保留末尾字符。来源 URL 仅接受 HTTP(S)，移除 userinfo、fragment 和敏感 query 参数值；external ID 进行长度限制和脱敏。飞书提醒从已规范化的安全正文派生，不再继续使用 raw text。

幂等记录的作用域升级为 `tenant + actor + operation + key`，并保存请求指纹。相同主体、相同 key、相同请求返回原结果；相同 key 对应不同请求返回稳定的 409；不同用户使用相同 key 是彼此独立的请求。任何旧资产返回仍必须通过当前 AccessContext 的授权查询。

数据库引入版本化迁移，不再依靠散落的 `CREATE TABLE IF NOT EXISTS` 与临时加列。迁移必须事务化、可重复启动、保留旧数据，并通过真实文件数据库升级测试。

### 3.2 身份边界

API 认证提供两种明确模式：

- `trusted_headers`：只允许 development/test，用于本机开发和现有测试。
- `bearer`：production 强制使用。Token 固定为 HS256，包含 issuer、audience、tenant、subject、roles、iat、exp 和唯一 ID；算法、签名、期限、issuer/audience 均严格验证。

Core 只接收验证后的 `AccessContext`，不接触 Fastify 请求或 Token。提供本地 Token 生成脚本，密钥只从环境变量读取，不允许出现在命令参数、源码或 Git 中。HMAC Token 是飞书 OAuth 接入前的安全过渡层，不冒充完整企业身份生命周期。

### 3.3 检索与资产生命周期

SQLite 使用 FTS5 把检索移动到数据库层，并在同一 SQL 中应用租户与 owner 权限条件。中文长词使用 trigram 召回，过短查询使用受限的安全 fallback；排序综合全文相关度、标题命中与新鲜度。索引由迁移回填并由资产写入/删除事务维护。

资产列表增加 cursor/limit、可见性和来源类型筛选，响应返回 `nextCursor`。新增按 ID 读取和所有者删除接口；删除同步清理 source、ingestion 与全文索引。资产删除暂采用物理删除，以满足本地试点的可验证清理语义；未来版本化资产和对象存储接入后再实现 tombstone + 异步删除传播。

### 3.4 Agent 与提醒

飞书文本先由指令路由识别：`帮助` 返回能力说明，`搜索 <问题>` 返回权限过滤后的证据，`问 <问题>` 返回带引用回答或安全降级证据。普通消息仍按现有规则入库并识别会议提醒。外部通知失败不得记录正文或密钥；本轮至少保留结构化失败日志和可重试状态边界，后续将回调处理迁移到 durable inbox/outbox worker。

提醒 API 增加手工创建能力，并严格验证 ISO 时间、提醒时间早于开始时间、状态转换及所有者边界。自然语言解析使用显式 `APP_TIMEZONE`，拒绝不存在的日期和已过去的明确时间。

## 4. 请求与错误数据流

产品请求的数据流为：

```text
HTTP request
→ request ID / body limit / rate limit
→ verified authentication principal
→ Zod validation
→ application service
→ repository query with tenant + actor policy
→ safe response / append-only operational log
```

飞书事件的数据流为：

```text
Feishu payload
→ decrypt + verification token validation
→ normalize event identity
→ command route or safe asset ingestion
→ permission-scoped search/answer or reminder extraction
→ outbound message adapter
```

错误统一为：

```json
{
  "error": "stable_machine_code",
  "message": "Safe human-readable message",
  "requestId": "fastify-request-id"
}
```

Malformed JSON、媒体类型、body 过大、认证、授权、不存在、幂等冲突、上游暂时失败和内部错误分别映射到 400、415、413、401/403、404、409、502/503 和 500。错误响应、日志和验证详情不回显用户正文、Token 或来源秘密。

## 5. 测试与发布

安全回归优先于功能测试：跨用户幂等攻击、同 key 不同 payload、短密码、标题/URL/externalId/提醒标题泄露、生产模式 trusted header 拒绝、Bearer 篡改/过期/错误 issuer、FTS 权限过滤和 501+ 资产均必须覆盖。

数据库测试使用 `:memory:` 快速单测与临时文件升级测试两层。API 契约覆盖 malformed JSON、413、415、404、409、requestId 和正文不回显。时间测试覆盖 UTC 进程环境、Asia/Shanghai 业务时区、月末/年末、非法日期和过去日期。飞书测试覆盖帮助、搜索、问答、无证据和 LLM 降级。

根级 `verify` 是唯一交付质量入口，PowerShell 包装链保持清晰。GitHub Actions 在 Windows 与 Linux/Node 24 运行安装、类型检查、测试和构建；依赖审计显式使用官方 npm registry。Docker 使用 Node 24 多阶段构建、非 root 用户、持久 SQLite volume 和 readiness healthcheck。文档同步更新能力矩阵、完整命令调用链、安全部署边界和后续路线。

## 6. 后续路线

v0.3 优先接入飞书 OAuth、租户成员与来源 ACL 快照、版本化 Asset/Chunk、删除传播和 append-only 审计；同时把飞书回调与通知迁入 durable inbox/outbox worker。随后以离线黄金问题集驱动 PostgreSQL FTS + vector 混合检索、精确段落引用和重排。Web/桌面入口、结构化记忆卡片、项目/客户 360 与经审批的跨系统 Agent 动作建立在这些边界稳定之后。
